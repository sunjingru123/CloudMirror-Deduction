- **项目地址**：<https://github.com/sunjingru123/CloudMirror-Deduction>
- **当前阶段**：第四阶段 · 恢复策略优化与推演历史记录（已完成）

## 2. 依赖方向与传播方向约定（务必统一）

> **边 `A → B` 表示「A 依赖 B」**，即 `source_node_id = A`（依赖方）、`target_node_id = B`（被依赖方）。

- 前端 Vue Flow 中，箭头由 A 指向 B（指向被依赖方），与后端字段一一对应。
- **故障传播方向与依赖方向相反**：依赖边 `A → B` ⇒ 传播路径 `B → A`，即 **B 故障时 A 可能受影响**。
- 算法通过构建**反向邻接表**实现：对每条依赖边 (A → B)，令 `dependents[B].append(A)`，
  再从故障源沿 `dependents` 扩散。
- 该约定在以下位置保持一致，避免「画布箭头方向」与「算法方向」不一致：
  - `backend/app/models/topology.py`
  - `backend/app/api/topologies.py`
  - `backend/app/services/topology_service.py`
  - `backend/app/services/propagation_service.py`
  - `frontend/src/api/topology.ts`
  - `frontend/src/components/TopologyNode.vue`（底部 source / 顶部 target）

示例：用户入口 → 负载均衡器 → 应用服务器 → 数据库（每个节点依赖其后一个节点）。
注入「数据库」故障时，传播方向为：数据库 → 应用服务器 → 负载均衡器 → 用户入口。

## 3. 三类「状态」的区分

1. **节点原始状态**：`topology_node.status`（`healthy` / `faulty` / `degraded`），
   表示节点自身的配置状态，注入故障不会改写它。
2. **激活的故障事件**：`fault_event` 中 `status = active` 的记录，表示「此刻正在发生的故障」。
3. **算法计算出的影响状态**：由传播分析服务根据拓扑与激活故障推导，仅存在于分析结果中。

## 5. 数据库表结构

| `description` | TEXT | NULL | 描述 |

### 5.2 `topology_node`（节点）

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | INTEGER | PK, 自增 | 主键 |
| `topology_id` | INTEGER | FK → `topology.id` ON DELETE CASCADE, INDEX | 所属拓扑 |
| `name` | VARCHAR(128) | NOT NULL | 节点名称 |
| `type` | VARCHAR(32) | NOT NULL | 节点类型（枚举校验） |

| `position_x` | FLOAT | NOT NULL, 默认 0 | 画布 X 坐标 |
| `position_y` | FLOAT | NOT NULL, 默认 0 | 画布 Y 坐标 |
| `created_at` | DATETIME | NOT NULL | 创建时间 |
| `updated_at` | DATETIME | NOT NULL | 更新时间 |

### 5.3 `topology_edge`（依赖关系）

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | INTEGER | PK, 自增 | 主键 |
| `topology_id` | INTEGER | FK → `topology.id` ON DELETE CASCADE, INDEX | 所属拓扑 |
| `source_node_id` | INTEGER | FK → `topology_node.id`, INDEX | 依赖方（source） |
| `target_node_id` | INTEGER | FK → `topology_node.id`, INDEX | 被依赖方（target） |
| `description` | TEXT | NULL | 依赖说明 |
| `created_at` | DATETIME | NOT NULL | 创建时间 |

**约束**：

- `UNIQUE (topology_id, source_node_id, target_node_id)`：防止重复边。
- `CHECK (source_node_id <> target_node_id)`：防止节点自依赖。
- 拓扑删除时级联删除其节点与依赖；节点删除时级联 / 显式删除相关依赖。
- 允许存在环路（A → B → C → A），传播算法需自行处理环路。

### 5.4 `fault_event`（故障事件）

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | INTEGER | PK, 自增 | 主键 |
| `topology_id` | INTEGER | FK → `topology.id` ON DELETE CASCADE, INDEX | 所属拓扑 |
| `source_node_id` | INTEGER | FK → `topology_node.id` ON DELETE CASCADE | 故障源节点 |
| `fault_type` | VARCHAR(32) | NOT NULL | 故障类型（枚举校验） |
| `severity` | VARCHAR(16) | NOT NULL | 严重程度（枚举校验） |
| `description` | TEXT | NULL | 故障描述 |
| `status` | VARCHAR(16) | NOT NULL, 默认 `active` | `active` / `recovered` |
| `created_at` | DATETIME | NOT NULL | 注入时间 |
| `recovered_at` | DATETIME | NULL | 恢复时间 |

**索引**：`(topology_id, status)`、`(source_node_id)`。

- 故障类型：`node_down`（节点宕机）、`service_unavailable`（服务不可用）、
  `network_latency`（网络延迟）、`network_unreachable`（网络不可达）。
- 严重程度：`low` / `medium` / `high` / `critical`。
- 同一节点允许多个**不同类型**的故障并存；对「同节点 + 同类型」的**激活**故障会被拒绝（`409`），
  已恢复的同类型故障不影响再次注入。
- 恢复故障只更新 `status` 与 `recovered_at`，**不删除历史记录**。

### 5.5 传播分析结果（规范化父子表）

| 表 | 说明 |
| --- | --- |
| `propagation_analysis` | 一次分析的汇总：`topology_id`、`fault_source_count`、`direct_affected_count`、`indirect_affected_count`、`total_affected_count`、`total_node_count`、`impact_ratio`、`analysis_time` |
| `analysis_fault_source` | 参与的故障源快照：`analysis_id`、`fault_id`、`node_id`、`node_name`、`fault_type`、`severity` |
| `analysis_affected_node` | 每个受影响节点：`analysis_id`、`node_id`、`node_name`、`impact_level`、`distance`、`source_fault_id`、`source_node_id` |
| `analysis_path_step` | 传播路径的有序步骤：`affected_node_id`、`step_index`、`node_id`、`node_name` |

分析结果**不使用无约束 JSON 大字段**，而是拆分为规范化的父子行，便于查询与校验。
子表通过 `ON DELETE CASCADE` 随分析记录删除；`node_id` / `fault_id` 使用 `ON DELETE SET NULL`
并保留名称快照，避免节点或故障被删除后丢失历史。

### 5.6 恢复策略（`recovery_plan` / `recovery_strategy` / `recovery_strategy_note`）

| 表 | 说明 |
| --- | --- |
| `recovery_plan` | 一次策略推荐：`id`、`topology_id`(FK, 级联)、`analysis_id`(FK → `propagation_analysis`, `SET NULL`)、`recommended_strategy_id`(软引用)、`recommendation_reason`、`estimation_notice`、`created_at` |
| `recovery_strategy` | 单个策略评估：`plan_id`(FK, 级联)、`strategy_type`(restart_service/failover/isolate_node)、`strategy_name`、`description`、`applicable`、`inapplicable_reason`、`estimated_recovery_time`、`estimated_affected_nodes`、`estimated_resource_cost`、`risk_level`、`recommendation_score` |
| `recovery_strategy_note` | 策略条目：`strategy_id`(FK, 级联)、`kind`(advantage/disadvantage/prerequisite)、`position`、`content` |

说明：

- 优势 / 劣势 / 前置条件拆分为有序子表，不使用 JSON 大字段。
- `recommended_strategy_id` 为**软引用**（不建外键）：`recovery_plan` 与 `recovery_strategy`
  若互相建外键会形成环，SQLite 建表排序会失败。该字段仅指向本计划内的一条策略。
- `estimated_*` 与 `recommendation_score` 均为**规则模拟估算值**，不是生产测量数据。

**SQLite 外键**：连接建立时通过 `PRAGMA foreign_keys=ON` 开启外键约束，
使 `ON DELETE CASCADE` / `SET NULL` 生效（见 `backend/app/core/database.py`）。

**幂等初始化**：使用 `Base.metadata.create_all()`，重复启动不会清空或重建数据。

## 7. 故障传播算法说明

实现位置：`backend/app/services/propagation_service.py`（独立 Service，不写在路由中）。

- **传播方向**：构建反向邻接表 `dependents[B] = [A, ...]`（A 依赖 B），
  从故障源沿 `dependents` 扩散，即「依赖故障源的节点会受影响」。
- **算法**：**多源 BFS（广度优先）**，边权重均为 1，故节点首次被发现的层级即为其最短传播距离。
- **多故障源**：所有激活故障源作为距离 0 的根同时入队；按 `fault_id` 升序、邻接按 `node_id`
  升序处理，保证结果**确定且可复现**。
- **环路处理**：以「已发现集合」`best` 做访问控制，节点仅在首次发现时写入并再次入队；
  环路不会死循环，也不会重复统计。
- **去重**：受影响节点以 `node_id` 为键去重；同一节点被多个故障源触达时保留距离最小者，
  距离相同则保留最先（按上述确定顺序）触达的故障源。
- **影响等级**：距离 1 为 `direct`（直接依赖故障源），距离 ≥ 2 为 `indirect`。
  故障源节点本身不计入受影响节点。
- **无激活故障**：返回空结果，不报错。
- **可复现性**：不涉及随机数、不调用大模型；结果完全由「拓扑结构 + 故障记录」决定。
- **冗余实例说明**：当前版本只输出影响范围与潜在风险，**不模拟**复杂负载均衡 / 冗余切换行为。

分析结果字段：`analysis_id`、`topology_id`、`fault_sources`、`affected_nodes`、
`direct_affected_count`、`indirect_affected_count`、`total_affected_count`、`total_node_count`、
`impact_ratio`、`propagation_paths`、`analysis_time`。每个受影响节点包含
`node_id`、`node_name`、`impact_level`、`distance`、`source_fault_id`、`propagation_path`。

## 8. 恢复策略服务说明

实现位置：`backend/app/services/recovery_service.py`（独立 Service），
参数与权重集中在 `backend/app/services/recovery_config.py`。

**输入**：当前拓扑的节点与依赖边 + 一次传播分析结果（含故障源快照）。

### 8.1 三类策略

| 策略 | 适用条件 | 估算恢复时间（秒） | 估算影响节点 | 资源成本 | 基础风险 |
| --- | --- | --- | --- | --- | --- |
| `restart_service` | 存在 `node_down` / `service_unavailable` 故障 | `120 + 60 × 可重启节点数` | 可重启节点数 | 低 | 中 |
| `failover` | 每个故障节点都有可用同类型备用节点 | `60 + 30 × 故障节点数` | 故障节点数 | 高 | 低 |
| `isolate_node` | 隔离后用户入口仍保留可用依赖 | `30 + 15 × 故障节点数` | 故障节点数 + 直接依赖方数 | 低 | 低 / 中 |

### 8.2 关键规则

- **备用节点不虚构**：项目尚未建立显式冗余关系模型。`failover` 仅在拓扑中存在
  「同类型、且既不是故障源、也不在本次分析影响范围内」的节点时判定为适用；
  否则 `applicable=false`，并在 `inapplicable_reason` 中列出具体缺失的节点。
- **隔离不保证恢复**：若某 `user_entry` 节点自身故障，或隔离后其**全部**直接依赖
  都处于故障状态，则 `isolate_node` 判定为不适用且风险为 `high`，永远不会被推荐。
- **网络类故障不适用重启**：故障全为 `network_latency` / `network_unreachable` 时，
  `restart_service` 不适用并给出原因。

### 8.3 评分模型（可解释的加权规则）

各分项先归一化到 `[0, 1]`，再按固定权重加权求和，最后 ×100：

| 分项 | 权重 | 归一化方式 |
| --- | --- | --- |
| 恢复时间 | 0.25 | `1 - min(t, 600) / 600` |
| 影响范围 | 0.20 | `1 - min(影响节点数, 节点总数) / 节点总数` |
| 资源成本 | 0.15 | 低 1.0 / 中 0.5 / 高 0.2 |
| 操作风险 | 0.20 | 低 1.0 / 中 0.6 / 高 0.2 |
| 业务恢复程度 | 0.20 | 重启 0.85 / 切换 0.95 / 隔离 0.35 |

- 权重合计 1.00，参考恢复时间 600 秒。
- **推荐规则**：仅在 `applicable=true` 的策略中取评分最高者；同分按固定顺序
  `restart_service → failover → isolate_node` 打破平局。不适用策略仍返回评分供参考，
  但**绝不会**成为推荐策略；若全部不适用，`recommended_strategy_id` 为 `null` 并解释原因。
- 不含随机数、不使用机器学习或大模型；相同输入必然得到相同输出，**完全可复现**。

### 8.4 推演历史

- 每次 `POST /analyze` 都会将结果落库，保存故障源与受影响节点的**名称快照**。
- `GET /topologies/{id}/analyses` 支持分页并按时间倒序，返回 `total`、`page`、`page_size`、`items`。
- `GET /topologies/{id}/analyses/{analysis_id}` 返回当时完整结果；跨拓扑读取返回 `404`。
- 故障恢复或节点删除后，历史记录仍可完整查看（快照字段不受影响）。

## 9. 前端实际操作流程

### 9.1 系统拓扑（`/topology`、`/topology/:id`）

1. **进入列表**：`GET /api/topologies` 加载拓扑；失败时页面顶部显示错误并提供「刷新」。
2. **新建拓扑**：点击「新建拓扑」→ 填写名称 / 描述 → `POST /api/topologies` → 自动进入编辑器。
3. **进入编辑器**：`GET /api/topologies/{id}` 读取节点与边，并在 Vue Flow 中真实渲染。
4. **添加节点**：右侧「添加节点」中点击某类型 → `POST .../nodes`（同时写入初始坐标）。
5. **拖动节点**：松手时 `PUT .../nodes/{id}` 自动保存坐标。
6. **创建依赖**：从节点**底部**圆点拖到另一节点**顶部**圆点 → `POST .../edges`；
   自依赖或重复边会被后端拒绝并弹出提示。
7. **选中节点**：点击节点 → 右侧面板编辑名称 / 类型 / 状态 / 描述 → 「保存节点」。
8. **删除节点 / 依赖**：选中后删除，相关依赖同步从前端移除。
9. **重命名 / 保存布局**：顶部按钮分别调用 `PUT /api/topologies/{id}` 与批量节点坐标更新。

### 9.2 故障模拟（`/fault-simulation`）

1. **选择拓扑**：下拉读取 `GET /api/topologies`；切换拓扑后加载其节点与故障
   （`GET /api/topologies/{id}`、`GET /api/topologies/{id}/faults`）。
2. **自动加载最近分析**：进入拓扑时静默调用 `GET .../analysis/latest`（无记录时忽略）
   并恢复画布高亮。
3. **注入故障**：选择节点、故障类型、严重程度、描述 → `POST .../faults`；
   非法操作（重复同类激活故障、节点不属于该拓扑）弹出后端返回的中文错误。
4. **查看 / 恢复故障**：故障列表展示全部事件（激活 / 已恢复）；激活项提供「恢复」按钮 →
   `POST /api/faults/{id}/recover`。
5. **开始传播分析**：点击「开始传播分析」→ `POST /api/topologies/{id}/analyze`（默认分析全部激活故障）。
6. **可视化**：故障源节点**红色**、直接影响节点**橙色**、间接影响节点**黄色**、正常节点保持原样；
   传播路径上的依赖边高亮并带流动动画；节点上显示影响等级与传播距离。
7. **查看详情**：点击节点，右侧面板显示其影响等级 / 距离 / 来源故障 / 完整传播路径。
8. **结果面板**：展示故障源数量、受影响节点数量、直接影响数、间接影响数、节点总数、
   影响比例与传播路径明细。
9. **清除高亮**：点击「清除高亮」恢复画布原状。

所有增删改与分析均调用真实后端 API，不使用本地假数据；加载 / 成功 / 失败均有明确反馈。

### 9.3 恢复策略（`/recovery`）

1. **选择拓扑**：下拉读取 `GET /api/topologies`。
2. **读取上下文**：切换拓扑时调用 `GET .../analysis/latest`（无记录时提示先分析）
   与 `GET .../recovery/strategies`（读取策略类型与评分权重）。
3. **运行传播分析**（可选）：「运行传播分析」调用 `POST .../analyze` 生成最新分析。
4. **生成策略对比**：「生成策略对比」调用 `POST .../recovery/recommend`
   （带上当前展示的 `analysis_id`），后端返回三类策略的适用性、估算指标与推荐结论。
5. **对比矩阵**：以矩阵形式并排比较预计恢复时间（含条形）、估算影响节点、资源成本、
   操作风险与综合评分；被推荐列高亮，不适用列淡化并单独展示**不适用原因**。
6. **策略明细**：每种策略展开优势 / 劣势 / 前置条件。
7. **推荐结论**：展示推荐理由与「模拟估算值」声明；页面底部展示评分权重来源。

### 9.4 历史记录（`/history`）

1. **选择拓扑**：切换拓扑后重新拉取第一页。
2. **历史列表**：`GET /api/topologies/{id}/analyses?page=&page_size=`，展示分析时间、
   拓扑名称、故障源数、直接影响数、间接影响数、总影响节点数、影响比例（含比例条）。
3. **分页**：页码 / 每页条数变化均调用真实后端接口，`total` 来自后端。
4. **查看详情**：点击「查看详情」调用 `GET .../analyses/{analysis_id}`，
   弹窗展示当时的指标、故障源列表与受影响节点（含影响等级、距离、传播路径）。

## 12. 开发约定

1. 使用 `main` 分支作为主干，功能开发建议使用独立分支后合并。
2. 遵循 `.gitignore` 约定：不提交 `.env`、密钥、数据库文件、虚拟环境、`node_modules`、构建产物。
3. 新增环境变量时同步更新对应的 `.env.example`（仅示例值）。
4. 文档中的功能状态须与实际实现保持一致，不得将未完成内容描述为已完成。
5. 传播算法必须放在独立 Service 中，不得塞进路由；不得使用随机数或大模型生成结果。
