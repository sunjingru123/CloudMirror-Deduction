# 云镜推演 · 比赛答辩 5 分钟演示流程

> 适用场景：比赛答辩 / 现场演示
> 目标：在 5 分钟内，用一条完整链路讲清「建拓扑 → 注入故障 → 传播分析 → 策略推荐 → 历史回溯」的闭环。
> 原则：**所有操作都走真实前后端接口**，不展示任何静态假数据。

---

## 一、演示前检查清单（提前 10 分钟完成）

| 检查项 | 命令 / 动作 | 期望 |
| --- | --- | --- |
| 后端已启动 | `cd backend` → 激活 venv → `uvicorn app.main:app --reload` | 终端出现 Uvicorn running |
| 后端健康 | 浏览器访问 `http://127.0.0.1:8000/api/health` | 返回状态与版本 JSON |
| 前端已启动 | `cd frontend` → `npm run dev` | 终端出现 Local: `http://127.0.0.1:5173` |
| 数据库干净 | 如有旧数据，删除 `backend/cloudmirror.db` 后重启后端 | 建表成功，无 500 |
| 演示数据就绪 | 提前建好 `电商核心链路` 拓扑（见附录） | 拓扑列表可见 |
| 浏览器准备 | Chrome / Edge，关闭无关标签，缩放到 100% | 画面完整 |
| 控制台干净 | 打开 F12，先确认无红色报错 | 无未捕获异常 |
| 网络稳定 | 关闭会弹窗的软件 / 通知 | 避免打扰 |

> 若现场网络受限，全部功能均为本地 `127.0.0.1` 通信，不依赖外网。

## 二、5 分钟时间轴

```mermaid
graph LR
    A["0:00 首页<br/>健康检查"] --> B["0:30 拓扑编辑<br/>搭链路+主备"]
    B --> C["1:30 故障注入<br/>数据库宕机"]
    C --> D["2:00 传播分析<br/>高亮+路径"]
    D --> E["2:45 恢复策略<br/>failover+估算声明"]
    E --> F["4:00 对比演示<br/>删冗余组→不适用"]
    F --> G["4:30 历史记录<br/>快照回溯"]
```

---

### 0:00 – 0:30 ｜ 首页：系统与后端连接

**操作**

1. 打开 `http://127.0.0.1:5173`，停留在「首页」。
2. 指出「后端连接状态」显示「已连接」，以及下方接口版本、项目名称。

**口播要点**

> 这是云镜推演的首页。它不读任何本地假数据，而是实时调用后端 `/api/health` 展示连接状态，说明「界面上的每一个结论都来自真实服务」。

**加分动作（可选）**

- 停掉后端 → 首页显示「后端未连接」并给出启动指引 → 重启后端 → 点「重新检测」恢复。
  用 10 秒证明「没有后端时页面不崩溃、也不假装成功」。

---

### 0:30 – 1:30 ｜ 系统拓扑：搭建业务与冗余

**操作**

1. 顶部导航进入「系统拓扑」，点击 `电商核心链路` 进入编辑页。
2. 指出已有链路：用户入口 → 负载均衡器 → 应用服务器 → 数据库（**箭头方向 = 依赖方向**）。
3. 拖动一个节点，松手提示「节点位置已保存」，证明坐标真实落库。
4. 打开「新建冗余组」，为主数据库建 active_standby 主备组：主节点 `数据库`，
   备用 `备数据库`（P1）、`备数据库二`（P2），保存。
5. 指出画布上的**紫色虚线**、节点「主节点 / 备用节点」徽标，以及画布下方图例。

**口播要点**

> 我们把业务依赖和冗余关系分开建模：灰实线箭头是依赖，紫虚线是显式主备关系。
> 这一点很关键——备用节点不是靠「同类型」猜出来的，而是显式声明的，后面 failover 只认这个。

---

### 1:30 – 2:00 ｜ 故障模拟：注入故障

**操作**

1. 导航进入「故障模拟」，选择 `电商核心链路`。
2. 右侧注入故障：故障节点选 `数据库`，故障类型选「节点宕机」(`node_down`)，
   严重程度选「严重」，描述填 `主库连接耗尽`，点击「注入故障」。
3. 展示右侧「故障事件（激活 1 / 共 1）」。

**口播要点**

> 故障是独立的事件记录，不篡改节点本身状态。这样历史可回溯，也允许同一节点存在多种故障、支持恢复。

---

### 2:00 – 2:45 ｜ 传播分析：算法与可视化

**操作**

1. 点击「开始传播分析」。
2. 展示「分析结果」指标：故障源 1 / 直接影响 / 间接影响 / 影响比例。
3. 指出画布配色：**红色**故障源、**橙色**直接影响、**黄色**间接影响；无关节点保持原样。
4. 点击一个间接受影响节点，展示右侧「影响等级 / 传播距离 / 来源故障 / 传播路径」。
5. 展示「传播路径明细」列表。

**口播要点**

> 传播方向不是「相邻节点」，而是沿依赖**反方向**逐层扩散：数据库宕机 → 应用服务器（直接）→ 负载均衡器 → 用户入口（间接）。
> 算法用 BFS 计算最短传播距离、记录完整路径，能处理环路、多故障源，并对受影响节点去重。
> 画布上的无关节点不会被误标——这证明结果是算出来的，不是画上去的。

---

### 2:45 – 4:00 ｜ 恢复策略：规则评分与显式冗余判定

**操作**

1. 导航进入「恢复策略」，确认目标拓扑，点击「运行传播分析」（如已有结果可跳过）。
2. 点击「生成策略对比」。
3. 展示策略对比矩阵：预计恢复时间 / 估算影响节点 / 资源成本 / 操作风险 / 综合评分 / 不适用原因。
4. 展开 failover 的「显式冗余判定」：冗余组名称、选中备用节点、选择理由。
5. 展开「备用节点候选（按 priority 升序）」与「前置条件检查」（✓/✕ 与说明）。
6. 指出顶部「推荐结论」与「模拟估算」声明、底部「评分规则」权重。

**口播要点**

> 恢复策略是可解释的加权规则，不是黑盒 AI：权重全部写在代码和页面里，可复现。
> failover 的每一步都要通过前置条件校验——是否有显式主备关系、备用是否正常、是否受传播影响、优先级是否明确。
> 备用节点按优先级升序选择，绝不随机。所有时间与成本都是**模拟估算值**，我们不做夸大。

---

### 4:00 – 4:30 ｜ 对比演示：删掉冗余组，failover 立即不适用

**操作**

1. 返回「系统拓扑」，在编辑页删除 `主数据库主备组`。
2. 回到「恢复策略」，点「刷新」后重新「生成策略对比」。
3. 展示 failover 变为「不适用」，并给出具体原因「未找到可用的显式备用节点…」。

**口播要点**

> 同一套故障、同一套算法，只因为去掉了显式冗余关系，切换方案立刻变得不适用。
> 这直接反驳了「用同类型节点冒充备用」的做法，也说明我们的结论完全由输入拓扑和故障记录决定，可复现。

---

### 4:30 – 5:00 ｜ 历史记录：快照回溯

**操作**

1. 导航进入「历史记录」，选择 `电商核心链路`。
2. 展示列表（分析时间 / 故障源数 / 直接影响 / 间接影响 / 总影响 / 影响比例）与分页。
3. 点击「查看详情」，展示当时完整快照：故障源、受影响节点、路径。

**口播要点**

> 每一次分析都以快照形式落库，即使后来恢复了故障、删除了节点，当时的分析与结论依然可以完整回溯。
> 这就是云镜推演：把「故障传播」和「恢复决策」变成可复现、可解释、可回溯的推演过程。

## 四、常见现场问题与应答

| 提问 | 应答要点 |
| --- | --- |
| 传播算法是不是随机/演示数据？ | 不是。BFS 按依赖反方向传播，结果只由拓扑与故障记录决定，可复现；页面注明无演示数据。 |
| 备用节点怎么来的？ | 只来自显式冗余组，不按同类型推断；不满足条件即 applicable=false 并说明原因。 |
| 评分是不是训练的 AI 模型？ | 不是。是可解释的固定权重加权规则，权重在代码与页面公开。 |
| 是不是真的能切流恢复生产？ | 不能。当前不执行真实切流，没有容量/网络/健康探测/数据同步校验，结果属虚拟推演与规则估算。 |
| 能处理环路吗？ | 能。算法通过访问标记避免重复与死循环，测试中已覆盖环路、多故障源场景。 |

## 附录：演示数据建议

- **拓扑**：`电商核心链路`
- **依赖（箭头为依赖方向）**：
  - 用户入口 → 负载均衡器
  - 负载均衡器 → 应用服务器
  - 应用服务器 → 数据库
- **无关节点**：缓存、外部 API
- **冗余组**：`主数据库主备组`（主备模式；主节点 `数据库`；备用 `备数据库` P1、`备数据库二` P2）
- **演示故障**：`数据库` · `node_down` · `critical`
